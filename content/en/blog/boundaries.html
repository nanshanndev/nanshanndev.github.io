A menu should know how to open, respond to arrow keys and display disabled items. It does not necessarily need to know a document’s permission model, a save endpoint or the business identity of an order.

nanshann recommends that components own presentation and local interaction, while business Behavior provides data, permissions and domain operations. Page HTML connects them through public inputs and events, with local actions handling any necessary orchestration.

Inputs are a usage contract

Components explicitly declare inputs with property() and attribute(). A menu might accept items and label, while keeping open state and its highlighted index private. Separating configuration from local state lets callers use a component without knowing its implementation.

Complex properties retain incoming references. Components consume caller-owned objects without mutation. Editing flows create explicit drafts and emit the user’s intent for business logic to handle.

Events describe what happened

A menu emits a native event with a command identifier. The page decides which document that command concerns and invokes the appropriate business action. Changing the menu’s layout or colors does not require rewriting document persistence.

Components can also expose host actions for imperative operations, such as focusing an input after ready. Inputs, events and actions each have a clear role.

Independent state, shared business logic

Each component instance creates its own state inside local Behavior. Shared business definitions are registered by name and created or released according to their consumers. They have no DOM region and do not implicitly belong to one page.

This division requires deliberate resource ownership. Creators register subscription, listener and request cleanup. Moving DOM does not automatically transfer those responsibilities.

Each component has at most one local Behavior. Ordinary logic can be composed from functions and modules. Use child components when UI needs an independent local lifecycle.
