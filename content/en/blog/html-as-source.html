An interface often lives in several places: a design describes its appearance, components organize its structure, and business code owns its data and operations. Keeping those sources aligned becomes a separate job.

nanshann chooses HTML as the shared editing source. Pages declare component references, public inputs and business events. Component definitions own internal structure, styling and local interactions. Agents and future design tools work with the same material.

Make dependencies visible where they are used

Readable source is only a starting point. An interface also needs to show where displayed data comes from, which action an interaction invokes, and what inputs a component exposes. Those contracts give changes a boundary and verification a concrete target.

A shared source keeps structure and relationships traceable.

Using HTML alone does not prove Agent friendliness. State, actions, dependencies and resource ownership still need explicit rules. Efficiency claims still need measurements on fixed tasks.

Shared definitions, page-level configuration

Page composition references components and adjusts arrangement, public configuration and business bindings. Changing internal HTML, CSS or Behavior is a component development task performed on the shared definition. Compatible visual updates should preserve existing business relationships.

This boundary avoids expanding component source into every page. Instances remain linked to their definitions while each keeps its own local state and resources.

Authoring tools are collaborators

A future page canvas and component editor can edit the same files while respecting their different responsibilities. Applications run independently of those tools and do not depend on another design-to-code artifact.

The visual editor and capability discovery tools are not implemented yet. HTML components and binding contracts already support independent code development.
