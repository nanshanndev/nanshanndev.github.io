“No application build” describes a runtime contract: the browser loads HTML, CSS and JavaScript ES Modules while nanshann parses component templates and establishes bindings in the browser.

It does not mean the framework repository has no development tooling. nanshann is developed in TypeScript; its distribution build produces browser ESM and declarations. Applications can then use those files directly with browser-executable code.

Start with two files

The entry index.html declares an import map, loads nanshann and references counter.html with ns-include. The component file contains structure, styling and a top-level Behavior. State changes update existing DOM through bindings.

This organization makes resource origins and runtime locations easier to follow. Ordinary static hosting is sufficient, and framework distribution stays separate from page authoring.

Respect browser boundaries

Native execution still follows URL, module and CSS rules. Relative imports in external modules resolve from the module URL. Inline Behavior uses Blob ESM, so dependencies are imported by import-map names or absolute URLs.

The browser parses CSS. Put relative stylesheet resources in external CSS so url() resolves against that stylesheet. Shadow DOM provides a style boundary, not a security sandbox.

Make deployment verifiable

Deploy the complete distribution, check MIME types and missing-resource responses, and verify under the actual CSP. History routing needs a document fallback; a multi-page site serves each HTML document directly.

Direct browser execution is a usage contract, not a performance ranking. Bundle size, long-term memory and Agent efficiency need separate measurements with defined conditions and methods.
